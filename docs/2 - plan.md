## Goal

Build a small, production-minded TypeScript webhook registry and dispatcher within the stated target of less than four hours.

The system will:

1. Accept and persist webhook subscriptions.
2. Accept and persist events.
3. Find subscriptions matching each event type.
4. Dispatch matching events asynchronously to subscriber webhook URLs using HTTP POST.
5. Persist delivery attempts and outcomes.
6. Provide delivery-status APIs as a bonus.
7. Include CloudFormation describing the AWS persistence/infrastructure.
8. Include automated tests and documented engineering standards.

## Scope and Priorities

### Must Have

- TypeScript service.
- CRUD API for `/subscriptions`.
- Event ingestion API at `/events`.
- Persistent external storage.
- Dispatcher that delivers matching events to subscriber URLs.
- Basic input validation and error handling.

### Strongly Recommended

- Persist events with durable IDs.
- Persist individual delivery records.
- Asynchronous dispatch rather than making `/events` wait for subscriber HTTP requests.
- HTTP timeouts.
- Clear delivery states.
- Retry handling for transient failures.
- Tests covering business logic and HTTP behavior.

### Bonus

- `/deliveries` endpoint(s).
- DynamoDB persistence.
- CloudFormation template.
- Recovery of incomplete/failed deliveries.
- Structured logging and useful operational metadata.
- Idempotency considerations.
- Health endpoint.
- API documentation.

## Proposed Implementation Sequence

### 1. Establish the Project

- TypeScript.
- HTTP framework with minimal unnecessary infrastructure.
- Strict TypeScript configuration.
- Linting/formatting.
- Test framework.
- Environment/configuration handling.

### 2. Define the Domain Model

Core entities:

- `Subscription`
- `Event`
- `Delivery`

A delivery represents the attempt/result relationship between one event and one subscription.

Relationship:

```text
Event
 ├── Delivery → Subscription → target URL
 ├── Delivery → Subscription → target URL
 └── Delivery → Subscription → target URL
 ```

 ### 3. Define Repository Interfaces

Keep persistence behind interfaces so the domain/application logic is not tightly coupled to DynamoDB.

Examples:

- `SubscriptionRepository`
- `EventRepository`
- `DeliveryRepository`

This allows an in-memory implementation for fast tests and a DynamoDB implementation for the real service.

### 4. Implement Subscription CRUD

Endpoints:

- `POST /subscriptions`
- `GET /subscriptions`
- `GET /subscriptions/{id}`
- `PUT /subscriptions/{id}`
- `DELETE /subscriptions/{id}`

Validate:

- event type is present and valid;
- target URL is a valid HTTPS URL;
- IDs are generated by the service.

### 5. Implement Event Ingestion

`POST /events` should:

1. Validate the event.
2. Generate an event ID.
3. Persist the event.
4. Initiate asynchronous dispatch.
5. Return without waiting for all webhook deliveries.

Prefer `202 Accepted` when dispatch is asynchronous.

The event must be persisted before dispatch begins so that an application crash does not lose the event after the API has accepted it.

### 6. Implement the Dispatcher

The dispatcher should:

1. Find subscriptions matching the event type.
2. Create delivery records.
3. Attempt delivery to each target URL.
4. Record success/failure information.
5. Apply bounded retry behavior for appropriate transient failures.

Do not let one subscriber failure prevent delivery to other subscribers.

### 7. Implement Recovery

The primary dispatch path should be immediate/asynchronous, not cron-based polling.

A periodic recovery mechanism may be used to find:

- pending deliveries;
- deliveries stuck in delivering;
- retryable failures.

Recovery exists to handle crashes/outages rather than to provide the normal dispatch path.

### 8. Implement `/deliveries`

Useful operations might include:

- `GET /deliveries`
- `GET /deliveries/{id}`

Support filtering by event ID, subscription ID, and status where practical.

### 9. Implement Persistence

Preferred challenge implementation:

- DynamoDB.

Design the table/indexes around actual access patterns rather than treating DynamoDB as a relational database.

If time is constrained, prioritize a correct repository abstraction and implementation over elaborate DynamoDB optimization.

### 10. Add CloudFormation

Provide a deployable-but-not-deployed CloudFormation template describing required AWS resources.

At minimum this should include the DynamoDB persistence resources used by the application.

If time permits, include useful outputs and configuration parameters.

### 11. Testing

Use a test pyramid:

```
             /\
            /E2E\
           /----\
          / Int. \
         /--------\
        /   Unit   \
       /------------\
```

Prioritize:

- many fast unit tests;
- a smaller number of integration/API tests;
- very few end-to-end tests.

Important behaviors to test include matching, persistence, successful delivery, failed delivery, retries, isolation between subscribers, validation, and recovery.

### 12. Final Production-Readiness Pass

Before packaging:

- remove secrets and local credentials;
- ensure configuration is environment-driven;
- verify useful error responses;
- verify HTTP timeouts;
- verify logging;
- verify tests;
- verify build from a clean checkout;
- verify CloudFormation syntax;
- include README with setup/run/test instructions;
- document deliberate tradeoffs and known limitations.

## Timebox

The four-hour constraint is important. Avoid building a distributed platform when a small service will satisfy the requirements.

Suggested allocation:

30 min: project setup, domain model, API shape.
60 min: subscriptions + persistence.
45 min: events + dispatcher.
45 min: delivery tracking + retries/recovery.
30 min: tests.
20 min: CloudFormation/configuration.
10 min: README, cleanup, ZIP verification.

If time runs short, prioritize correctness of the core flow over bonus infrastructure.
